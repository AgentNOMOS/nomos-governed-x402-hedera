# Security Boundaries

This repository was carved out of a larger, live production estate. That estate
runs real payment routes, holds real signing keys and is under an active
observation window. **None of it may be touched, copied, referenced as a
runtime dependency, or published.**

This document states the boundary precisely, because a boundary that lives only
in someone's head is not a boundary.

---

## 1. What this project may never do

| # | Prohibition | Enforced by |
|---|---|---|
| B1 | Use any pre-existing Hedera **account** from the production estate | `.env.example` warns; every fixture uses the synthetic `0.0.999xxx` range |
| B2 | Write to any pre-existing HCS **topic** | `assertTopicAllowed()` throws `TopicBoundaryError` for `0.0.10420280`, `0.0.10420282`, `0.0.8510520`, `0.0.8510521` |
| B3 | Load a **signing key** from the production tree | `LocalEd25519Signer.fromFile()` refuses paths under `/srv/nomos/signing`, `/srv/nomos/verify`, `/opt/nomos-*`, `/root/.hedera-*`, and the SEC-HEDERA-A1 quarantine |
| B4 | Reuse any **quarantined or previously-exposed** key material | No code path reads any of it; see §3 |
| B5 | Touch **mainnet** | `network` is pinned to `hedera:testnet` by JSON-Schema `const`; a mainnet document is unrepresentable |
| B6 | Import or vendor a **production module** | Zero imports outside this repository and the Node standard library |
| B7 | Modify the production **x402 gateway**, units, timers or cronjobs | This repo contains no deployment artifact of any kind |
| B8 | Publish **request or result content** on-chain | The anchor payload type has five fields and none can hold content |
| B9 | Commit a **secret** | `tools/secret-scan.ts`, run by `npm run check` and by a test |

## 2. Why the pre-existing Hedera assets are excluded

A forensic assessment (`HEDERA_NOMOS_X402_REUSE_ASSESSMENT.md`, 2026-07-22)
found working Hedera Consensus Service code and a funded testnet account in the
existing estate. Both were excluded, for different reasons:

**The mainnet topic `0.0.10420280`** carries 297 real messages from a production
beacon. Writing demo data to it would pollute a permanent, public, unalterable
record that other systems reference.

**The testnet account `0.0.8509917`** holds ~999.7 HBAR and would have saved a
faucet round-trip. Its operator key, however, lived in the same `.env` file that
was the subject of a key-exposure incident (SEC-HEDERA-A1, 2026-06-12), and now
exists only inside a quarantine directory. Reusing it would mean reactivating a
compromised credential to save five minutes. It is treated as burned.

Both decisions point the same way, which is a good sign: the isolation the
bounty demands and the isolation security demands are the same isolation.

## 3. Key custody

Three kinds of key exist in this design. They are deliberately different keys.

| Key | Held by | Touches | Notes |
|---|---|---|---|
| **Payer key** | the isolated `PaymentSigner` process, never the agent | Hedera transactions | The signer takes bytes and returns bytes. Nothing in the interface graph has a field a key could travel through. Swappable for an HSM, KMS or the Hiero CLI. |
| **Receipt signing key** | the resource server | Nothing on-chain | Throwaway, generated by `npm run keygen`, mode 0600, git-ignored. Its own signature domain. |
| **Agent identity key** | the agent | Nothing on-chain today | Identifies who acted. |

Rules that hold for all three:

* No key value is ever written to a log, a receipt, an error message, a test
  fixture or an HCS message.
* No key is ever passed to, or reachable from, an LLM context.
* `.gitignore` excludes `*.key`, `*.pem`, `.env`, `.local/` and wallet-shaped
  filenames; `tools/secret-scan.ts` fails the build on key-shaped content.

## 4. What may be published

Publishable: the protocol, the schemas, the policy logic, the canonicalization
profile, the receipt format, the verifier, the tests, and any HashScan links to
**testnet** transactions this project itself creates.

Not publishable: anything derived from the production estate — internal
hostnames and ports, production account ids, revenue figures, ledger contents,
production policy documents, or the production issuer's public key.

## 5. On-chain data minimisation

An HCS message is public and permanent. Anchoring publishes exactly this:

```json
{ "t": "nomos.gx402.anchor.v1",
  "d": "sha256:<record digest>",
  "r": "poa_<receipt id>",
  "ts": "2026-07-22T12:00:00Z",
  "env": "TESTNET_DEMO_ONLY" }
```

No subject, no request body, no result, no account beyond the payer implied by
the submitting transaction. The receipt itself already excludes content by
construction — it carries `request_hash` and `result_hash`, never the values
they commit to.

## 6. Verification you can run

```bash
npm run scan     # secret scan; fails on key material or production leakage
npm test         # includes the boundary tests below
```

The boundary tests assert, as executable claims:

* the forbidden topic ids are refused (`tests/unit/anchor.test.ts`)
* the forbidden key paths are refused (`tests/unit/receipt.test.ts`)
* a mainnet network value cannot validate (`tests/unit/schemas.test.ts`)
* the receipt leaks neither the request subject nor result content
  (`tests/integration/flow.test.ts`)
* the repository contains no committed secret (`tests/unit/secret-scan.test.ts`)
